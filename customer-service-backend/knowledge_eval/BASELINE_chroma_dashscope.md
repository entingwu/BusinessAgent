# 改造前基线 — Chroma + DashScope text-embedding-v3

冻结于 `64821b6`（改造起点）。这份数字的用途只有一个：**证明 Milvus + BGE-M3 + RRF + rerank
的改造是进步而不是退步。** 改造完成后用同一份 `calibration_set.jsonl` 复跑，逐项对照。

没有这份基线，「换了更先进的技术栈」只是一句无法证伪的话。

## 配置

| 项 | 值 |
|---|---|
| Embedding | DashScope `text-embedding-v3`，1024 维，托管 API |
| 向量库 | Chroma，本地持久化目录，纯 dense 检索 |
| 检索 | 余弦 Top-K=5 + 阈值 + metadata 过滤 |
| 阈值 | `KNOWLEDGE_SCORE_THRESHOLD=0.58` |
| 语料 | 45 片（FAQ 22 + 政策文档 23），5 个知识源 |
| 评测集 | `calibration_set.jsonl`，34 条（有答案 22 / 无答案 12） |

## 检索质量

| 指标 | 基线值 |
|---|---|
| 有答案用例召回 | **22 / 22** |
| 无答案用例正确兜底 | **11 / 12** |
| 误通过（靠提示词第二道防线挡住） | 1 条：「支持货到付款吗」top=0.7263 |
| 有答案组最低分 | 0.6030（衣服吊牌剪了还能退吗） |
| 无答案组最高分 | 0.7263（同上误通过项） |
| 剥离该离群点后的可分区间 | (0.5605, 0.6030)，中点 0.5817 |

**区间重叠只剩一个离群点。** 「支持货到付款吗」与「支持海外或港澳台配送吗？」表面句式高度相似，
是 Embedding 对短问句的表面相似，不是切分问题（切分方案已按规范 C.4.6 调整过一轮）。

## 延迟

单条检索（含一次 embedding API 调用 + 向量检索，不含 LLM 生成）约 **0.68–0.85 秒**，
取自 calibrate 全程 34 条的日志时间戳间隔。

> 这一项改造后大概率会变差：BGE-M3 在本机走 CPU（M1 Max 无 CUDA，`use_fp16` 不可用），
> 且链路上多了 HyDE 的一次 LLM 调用与一次 rerank API 调用。**变差多少要量，不能估。**

## 改造后必须对照的项

1. 有答案召回 —— 不得低于 22/22
2. 无答案兜底 —— 不得低于 11/12，目标 12/12
3. 「支持货到付款吗」那条误通过 —— 混合检索的 sparse 分量理论上能区分「货到付款」与「海外配送」，
   这是本次改造**最该兑现的一条**。若仍误通过，说明 RRF 与 rerank 没有解决实际问题
4. 端到端延迟 —— 记录即可，允许变差，但要知道差多少
5. 「未命中不调 LLM」的机制保证 —— **不得被 LangGraph 改写破坏**，这是验收第 3 条的红线
